Part 1 · How a drawing gets on the page today

Think of src/entities/handwriting.ts as a list of stickers. Each entry says: which JSON file, where on the canvas, how wide, and optionally a name (triggerId). App.tsx loops over the list and puts one component on the canvas per entry. That component fetches the JSON and draws the strokes one by one with a timer. If the entry has a name, the component signs up in a phone book so anyone can call it later.

// one sticker in the list
handwriting({
  id: 'hw-welcome-2',
  x: 74, y: 72, width: 600,                 // canvas is 8000 x 8000 px, x and y are percentages
  src: '/handwriting/second-new.json',      // the strokes you recorded
  triggerId: 'welcome-2',                   // its name in the phone book
  revealMode: 'manual',                     // stay invisible until someone calls play()
})

Part 2 · What a click will do (new)

Right now the drawing's wrapper has pointer-events: none, so a click goes straight through to the canvas and pans. The change: let the ink itself catch the click, then run a short checklist.

// the whole thing, in plain words
function onInkClick(entity) {
  if (progress < 1) return                              // not finished → the click falls through
  if (entity.enabledWhen && !guards.check(entity.enabledWhen)) return   // optional rule
  for (const item of list(entity.onClickAction)) {      // 'trigger:welcome-2', 'sfx:/sounds/chalk.mp3'
    const [kind, arg] = item.split(':')
    actions[kind](ctx, arg)                              // trigger → triggers.play(arg)
  }
}

Clicking A should make B appear. Somebody has to write that down. Two choices, same behaviour, different bookkeeping.

Part 4 · The other half of block 6: where do the numbers come from?

Every entry needs x and y. The canvas is 8000 by 8000 pixels and positions are percentages, so x: 74 means 5920 px from the left. Guessing those by hand and refreshing is slow. Three ways to get them:

  1. Dev overlay. Press a key in dev mode. Every drawing becomes draggable and shows a small tag with its live x and y. Drag it where it looks right, copy the two numbers into the entry. MotionObstacle already has this readout behind showPosition; this generalises it.
  2. Relative helpers. Write ...rightOf('hw-welcome-1', 2) instead of numbers. Fine for chains that read left to right, awkward for anything freeform.
  3. Type and iterate. Guess, save, look, adjust. Zero code, slowest loop.

Block 4, closed · reveal sources, and does scenes.ts survive?

Today Play runs a fixed script: pan the camera, start welcome-1, wait 17 seconds, pan, start welcome-2, and so on. You asked for both freedoms: clicks drive the show, and things can still appear on their own after a while. With 1b that is one field with more than one value.

// reveal sources — a drawing may list several, first one wins
revealedBy: 'click:button-1'                        // the Play button is just another clickable entity
revealedBy: 'load +2s'                              // appears 2 s after the page loads
revealedBy: ['click:welcome-1', 'done:welcome-1 +3s']  // click it, or wait 3 s after it finishes drawing

// what scenes.ts holds today, and where it would go
//   triggerId     → the entity itself
//   focus (camera)→ camera: { zoom: 0.9 }  on the entity, position already known
//   sfx           → onReveal: 'sfx:/sounds/chalk-7s.mp3'
//   holdDuration  → 'done:welcome-1 +3s' on the next drawing (the JSON length is known)
//   order         → the chain of done: / click: sources

If every row above moves onto the entities, scenes.ts has nothing left and MotionController shrinks to two jobs: pan the camera when a drawing with camera is revealed, and fire done: when a drawing finishes. Staged: build the click chain first with scenes.ts untouched, then migrate the three existing scenes.

Decided 2026-11-01: sources click:, done: +Ns, load +Ns, arrays with first-wins. scenes.ts folds into the entities as a second step.

Block 5, closed · where do the new fields live?

Six new fields came out of blocks 3, 4 and 6. The question is how wide they apply.

fieldfrommeaning
revealedByblocks 6, 4how this entity appears: 'load', 'static', 'click:A', 'done:A +3s', or a list
clickableblock 3the ink catches clicks once finished
onClickActionblock 3to-do list on click: link:, sfx:, pan:
enabledWhenblock 3optional guard before the to-do list runs
onRevealblock 4to-do list when it appears, usually sfx:
camerablock 4pan and zoom to it when it is revealed
  • Recommended: universal. The six fields live on EntityDef, so any entity can be revealed or clicked: a PNG sketch fading in after a click, a photo section appearing when a drawing finishes. Built first for handwriting and the button; the rest become small follow-ups. Alternative: handwriting only. Smaller surface, but the first time you want a sketch to appear on click you are back here.
  • Retire two fields. revealMode and autoplay are both covered by revealedBy. The five existing entries get rewritten.
  • One name. triggerId defaults to id; it stays as an optional alias so the old scenes keep working during the staged migration.
  • No new type. object-types.md gets one shared "Reveal and click" section instead of a new row.

Decided 2026-11-01: universal, one source of truth. And normalized: every entity carries every field, with explicit defaults when unused, the way every row in a table has every column.

Blocks 7 and 8, closed

Block 7 · the checklist, as decided

  • Phones. Under 4 px of movement is a click, more is a pan. Two fingers never click.
  • Reduced motion. The ink animation always plays; it is the point of the site. Camera pans become instant cuts, since pans and zooms are what cause discomfort.
  • Keyboard. No Tab stops for now. Every entity carries tabOrder: null; set a number and that drawing becomes focusable, in that order, with Enter running the click list.
  • Performance. The drawing loop is rewritten now: each finished stroke is computed once and cached, only the stroke being drawn is recomputed, and the loop writes to the DOM directly instead of a React state update per frame. Same pattern as useJitter and ZoomCanvas. Only HandwrittenEntry.tsx changes; its props, handle and pixels stay the same.

Block 8 · routes, as decided

  • Hash URLs. /#/freshpage1. Everything after # stays in the browser, so the server only ever serves index.html and refresh always works with zero Vercel config. The route is read through one currentRoute() function, so switching to clean paths later is one line plus a Vercel rewrite.
  • A notebook per route. { entities, pages } picked by route. Home is today's content; freshpage1 starts empty. TopHeader stays outside and gets one link per notebook.
  • Two kinds of state. Canvas state (zoom, pan, positions, pins, phone book) resets per notebook. Visitor preferences (mute) and visitor progress (played, flags) persist across notebooks and reloads in localStorage.
  • Unique logic on reaching a sketch. onReveal: 'fn:unlockSecret' runs your function, set:secret writes a flag, enabledWhen: 'flag:secret' reads it elsewhere.
